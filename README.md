# 保养事件离线补传演示

工位控制器离线缓存保养**开始/结束/复核**事件，上线后按不同大小的包补传；接收端只确认已持久化的序号，工单端不得跨过缺失的开始事件把结束定为已完成。仅用 Node.js 内置模块，不接外部服务。

## 运行

```bash
node server.js        # 读取 PORT（默认 3000），绑定 127.0.0.1
PORT=8080 node server.js
```

打开 `http://127.0.0.1:3000`，同一次操作里依次点：

1. **接收不连续保养包** — 上线后按 2 条、4 条组包补传，第二包模拟丢失 seq=3（WO-1002 的开始事件）。结果：高水位=2、缺口=[3]，WO-1002 为 `blocked_missing_start`（结束事件已到也不得定为已完成）。
2. **补齐开始事件** — 发送端按缺口清单只重传 seq=3（包大小=缺口数），高水位推进到 6，WO-1002 转为 `reviewed`。
3. **查看工单回执** — 两张工单的状态、版本、已应用序号。

另可点 **复核回退 WO-1001** → **重发旧包**：旧版本复核包被标记 `stale`（旧状态），工单停在 `completed` 不被改回。业务结果区带 `data-evidence-result` 属性，每次操作更新为最新 JSON，便于核对前后内容。

## 设计要点

- **确认方式：连续高水位 + 缺口清单** `{ highWatermark, gaps, maxSeen }`。纯高水位在掉线补传时会迫使重传缺口之后的所有包；纯逐条确认的 ACK 随离线时长膨胀。组合方式让发送端只保留缺口序号待重传（`Controller.handleAck`），兼顾补传效率与队列大小。
- **只确认已持久化**：事件先写盘（`data/events.jsonl`）再进入可确认集合；重启后从日志恢复，确认结果一致。
- **工单投影**：由持久化且非旧状态的事件推导；缺开始事件时结束事件照常落盘，但工单为 `blocked_missing_start`，不得定为已完成。
- **旧状态识别**：复核回退使工单版本 +1；版本只约束复核事件（开始/结束是事实不随回退失效）。重发的旧复核包 `version < currentVersion` 即 `stale`，落盘留痕但不参与投影。

## 测试

```bash
node --test
```
